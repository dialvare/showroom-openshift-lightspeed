[#prepare-the-bastion]
== Prepare the bastion

Most of the work in this module happens in the *Bastion* tab (the terminal connected to the cluster's bastion host). Start by installing podman:

[source,bash,role="execute"]
----
sudo dnf install -y podman
----

Then create a working directory for the exercise:

[source,bash,role="execute"]
----
mkdir -p ~/byok/markdown ~/byok/output && cd ~/byok
----

[#write-the-documentation]
== Write the documentation

Let's give ACME Corp one more internal document: their disaster recovery drill procedure.

Now create the Markdown document. Note the metadata block at the top: the BYOK Knowledge tool uses the _title_ and _url_ attributes as the source reference that the assistant displays alongside its answers. If you omit them, the first heading becomes the title and the file path becomes the URL.

[source,bash,role="execute"]
----
cat > markdown/dr-drills.md <<'EOF'
---
title: "ACME Corp disaster recovery drill procedure for OpenShift"
url: "https://wiki.acme.example/openshift/dr-drills"
---

# ACME Corp disaster recovery drill procedure for OpenShift

ACME Corp requires every production OpenShift cluster to complete a disaster
recovery (DR) drill once per quarter. Drills are coordinated by the Platform
Reliability team and tracked in the ACME-DR Jira project.

## Drill requirements

- DR drills must be scheduled at least two weeks in advance through the
  ACME-DR Jira project.
- The drill must simulate the loss of one availability zone by cordoning and
  draining all nodes in that zone.
- etcd backups must be restored to the staging cluster `acme-dr-staging` and
  validated by the application teams.
- The maximum tolerated recovery time objective (RTO) at ACME Corp is
  45 minutes. Drills that exceed 45 minutes must be repeated within 30 days.

## Sign-off

After a successful drill, the Platform Reliability team lead records the
results in the ACME-DR Jira project and notifies the compliance team via the
#acme-compliance Slack channel. Compliance sign-off is mandatory before the
next production change window opens.
EOF
----

Feel free to write your own document instead: anything the base model couldn't possibly know makes for a convincing test.

[#get-the-rag-tool-image]
== Get the BYOK Knowledge tool image

The BYOK Knowledge tool ships as a container image on registry.redhat.io, which requires authentication to pull. The official procedure assumes you have your own Red Hat registry account, but in this lab you can borrow the cluster's pull secret instead, since it already contains registry credentials:

[source,bash,role="execute"]
----
oc extract secret/pull-secret -n openshift-config --confirm --to=$HOME/byok
----

Install the pull secret as podman's credentials file, so every podman command (including the ones inside the BYOK Knowledge tool) can use it:

[source,bash,role="execute"]
----
mkdir -p $XDG_RUNTIME_DIR/containers
cp $HOME/byok/.dockerconfigjson $XDG_RUNTIME_DIR/containers/auth.json
----

[source,bash,role="execute"]
----
podman pull registry.redhat.io/openshift-lightspeed-tech-preview/lightspeed-rag-tool-rhel9:latest
----

NOTE: The BYOK Knowledge tool image is large (it bundles the embedding model), so the pull takes a few minutes.

[#generate-the-image]
== Generate the BYOK image

The tool also builds the output image internally, and for that it needs two small adjustments: a storage configuration that works inside a container, and a public base image. Prepare the storage configuration:

[source,bash,role="execute"]
----
cat > ~/byok/tool-storage.conf <<'EOF'
[storage]
driver = "vfs"
graphroot = "/var/lib/containers/storage"
runroot = "/run/containers/storage"
EOF
----

Now run the tool, passing the base image override and your Markdown and output directories:

[source,bash,role="execute"]
----
podman run -it --rm \
  -e UBI_BASE_IMAGE=registry.access.redhat.com/ubi9/ubi:latest \
  -v $XDG_RUNTIME_DIR/containers/auth.json:/run/user/0/containers/auth.json:Z \
  -v ~/byok/tool-storage.conf:/etc/containers/storage.conf:ro,Z \
  -v ~/byok/markdown:/markdown:Z \
  -v ~/byok/output:/output:Z \
  registry.redhat.io/openshift-lightspeed-tech-preview/lightspeed-rag-tool-rhel9:latest
----

The BYOK Knowledge tool chunks your Markdown, runs it through the embedding model (watch for your document's title in the logs), builds the image, and writes it as a tarball to the output directory.

When the tool finishes, you will find the generated image tarball in the output directory:

[source,bash,role="execute"]
----
ls -lh ~/byok/output
----

Load it into podman, as in the official procedure:

[source,bash,role="execute"]
----
podman load < ~/byok/output/*.tar
----

Check that the image is loaded. It is named `byok-image`:

[source,bash,role="execute"]
----
podman images
----

[#push-the-image]
== Push the image to the internal registry

Instead of an external registry such as quay.io, you will push the image to the cluster's internal image registry. First, create a project to hold the image (the internal registry maps projects to repositories):

[source,bash,role="execute"]
----
oc new-project byok-workshop
----

Then expose the registry outside the cluster, wait for it to settle, and store its address in a variable:

[source,bash,role="execute"]
----
oc patch configs.imageregistry.operator.openshift.io cluster --type merge -p '{"spec":{"defaultRoute":true}}' > /dev/null
REGISTRY=$(oc get route default-route -n openshift-image-registry -o jsonpath='{.spec.host}')
echo $REGISTRY
----

[source,bash,role="execute"]
----
oc wait --for=condition=Available deployment/image-registry -n openshift-image-registry --timeout=180s
----

NOTE: Exposing the registry makes the image registry operator roll the registry pods, and on this single-node cluster the API can briefly return errors while that happens. The wait command above retries until the registry is back. If an `oc` command fails around this point, give it a minute and try again.

Finally, log in to the registry with podman. The bastion's `oc` session is certificate-based and cannot produce a login token, so create one for the `builder` service account, which has push permissions in its project:

[source,bash,role="execute"]
----
TOKEN=$(oc create token builder -n byok-workshop --duration=8h)
podman login -u builder -p $TOKEN $REGISTRY
----

Tag the generated image with its destination and push it:

[source,bash,role="execute"]
----
podman tag localhost/byok-image:latest $REGISTRY/byok-workshop/acme-dr-byok:latest
----

[source,bash,role="execute"]
----
podman push $REGISTRY/byok-workshop/acme-dr-byok:latest
----

[#connect-it-to-lightspeed]
== Connect it to OpenShift Lightspeed

OpenShift Lightspeed runs in the `openshift-lightspeed` namespace, so its service accounts need permission to pull images from your `byok-workshop` namespace. Grant it:

[source,bash,role="execute"]
----
oc policy add-role-to-group system:image-puller system:serviceaccounts:openshift-lightspeed -n byok-workshop
----

NOTE: The command prints _Warning: Group 'system:serviceaccounts:openshift-lightspeed' not found_. That is expected: it is a _virtual_ group representing every service account in that namespace, so no Group object exists. The role binding is created regardless.

Now add your image as a second RAG database. From within the cluster, the image you pushed is known by its internal name, so that is what OpenShift Lightspeed will reference.

As in the previous module, navigate to *Ecosystem* -> *Installed Operators* -> *OpenShift Lightspeed Operator* -> *OLSConfig* -> `cluster` -> *YAML*, and extend the _rag_ list:

----
...
spec:
...
  ols:
...
    rag:
      - image: 'quay.io/dialvare/acme-byok:latest'
        indexID: ''
        indexPath: /rag/vector_db
      - image: 'image-registry.openshift-image-registry.svc:5000/byok-workshop/acme-dr-byok:latest'
        indexID: ''
        indexPath: /rag/vector_db
----

Click *Save*. The OpenShift Lightspeed app server pod redeploys to load the new database. Give it a minute or two.

[#test-your-knowledge]
== Test your knowledge

Open the chatbot interface, click the *Clear chat* (trash can) button if needed, and ask:

[source,role="copypaste"]
----
What is the ACME Corp procedure for disaster recovery drills on OpenShift?
----

The answer should walk through exactly what you wrote: the two-week scheduling requirement in the ACME-DR Jira project, the 45-minute RTO, and the compliance sign-off via the #acme-compliance Slack channel. Scroll to the bottom of the response and you will also find your document's title (_ACME Corp disaster recovery drill procedure for OpenShift_) listed among the referenced sources, exactly as the title metadata promised.

TIP: Because your image uses the floating _latest_ tag, OpenShift Lightspeed keeps it fresh automatically: image changes are detected through ImageStream objects, which the cluster rechecks every 15 minutes. Rebuild the image with updated docs and the assistant's knowledge follows, with no OLSConfig edits required.
