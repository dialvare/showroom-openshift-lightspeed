= AI-assisted Cluster Updates

include::partial$console-access.adoc[]

Cluster updates are one of the most critical — and nerve-wracking — tasks for an operations team. A single overlooked condition can turn a routine upgrade into an incident. This module brings together the two capabilities you have been using throughout the lab: the intelligent assistant, which can assess your cluster's readiness for an update from the web console, and OpenShift Lightspeed autonomous agents, which power the deeper analysis behind those assessments.

[#precheck-your-cluster-with-ai]
== Precheck Your Cluster with AI

Before triggering an update, you can ask the intelligent assistant to analyze your cluster's health and flag potential blockers, making the update process more predictable and secure.

Navigate to *Administration* -> *Cluster Settings* in the OpenShift web console. In the *Details* page you should see an AI assessment section indicating that updates are available.

image::ols-cluster-update.png[AI-assisted cluster updates, align="center", link=self, window=blank]

Select *Precheck your cluster with AI*. The chatbot interface opens automatically and starts investigating your cluster's status, assessing whether it is ready for the upgrade — the same autonomous investigation you used in the Troubleshooting module, now applied to update readiness.

[#agentic-runs-from-the-cluster-version-operator]
== Agentic Runs from the Cluster Version Operator

The precheck you just ran was conversational: you asked, and the assistant investigated. Behind the scenes, cluster updates are also the third way `AgenticRun` resources get created — the one you already glimpsed in the previous module, where runs created by the Cluster Version Operator sat alongside your own in a *Pending* state.

When an upgrade path is available in your cluster, the Cluster Version Operator automatically creates `AgenticRun` resources to analyze the recommended and conditional update targets. Instead of you describing the problem, the cluster itself describes it: each run investigates whether the cluster can safely move to a specific version, so potential blockers surface before you commit to the update. The same human-in-the-loop approvals you used in the previous module apply here too — Analysis and Execution wait for your sign-off before anything touches the cluster.
