= OpenShift Lightspeed autonomous agents

include::partial$console-access.adoc[]

So far in this lab, the OpenShift Lightspeed intelligent assistant has always waited for you to start the conversation. You asked the questions, you decided when to approve tool calls, and you chose what to investigate next. OpenShift Lightspeed autonomous agents change that dynamic. Given a plain-language description of a problem, they can autonomously investigate root causes, propose a remediation plan, apply the approved fix, and verify the outcome, all without you having to find the right YAML, attach the right resource, or compose the right follow-up question.

The core building block of OpenShift Lightspeed autonomous agents is the `AgenticRun` custom resource. Each run goes through the following lifecycle:

* *Analysis*: the agent investigates the issue and proposes remediation options.
* *Execution*: the approved option is applied to the cluster.
* *Verification*: the agent confirms the fix worked.
* *Escalation*: triggered only if Verification fails, creating a record of what failed for human review.

Every phase runs in a short-lived sandbox pod that calls the LLM and exits when its step is done. The human-in-the-loop configuration lives in an `ApprovalPolicy` custom resource, where a cluster admin can define which phases run automatically and which require a human to approve or reject before proceeding.

Besides manually creating AgenticRuns, you can also rely on the *Alerts Adapter*, a companion service that polls Alertmanager and automatically creates AgenticRun CRs when firing alerts match a configured severity, closing the loop for fully autonomous remediation.

In this module you work with OpenShift Lightspeed autonomous agents: manually creating an AgenticRun, enabling the Alerts Adapter for automatic triggering, and following each run through its full lifecycle.

NOTE: The Alerts Adapter is deployed but its severity filter is commented out, so it is not creating any runs yet. You will enable it in the last exercise.

[#pre-deployed-resources]
== Exploring pre-deployed resources

Let's get familiar with the building blocks that were pre-configured for you, directly from the OpenShift web console.

Navigate to *Home* -> *Search* in the left navigation menu. Make sure the *Project* dropdown at the top is set to `openshift-lightspeed`.

image::search-menu.png[Search menu in OpenShift web console, align="center", link=self, window=blank]

Now use the *Resources* box to search for the following custom resources:

==== *LLMProvider*

In the *Resources* box, type `LLMProvider` and select it from the drop-down. You will see the `maas` provider listed. Click on it and open the *YAML* tab, where you should see something similar to the following:

----
apiVersion: agentic.openshift.io/v1alpha1
kind: LLMProvider
metadata:
  name: maas
spec:
  openAI:
    credentialsSecret:
      name: llm-creds-maas
    url: 'https://maas-rhdp.apps.maas.redhatworkshops.io/v1'
  type: OpenAI
----

The provider points to the Model-as-a-Service (MaaS) endpoint and reads credentials from the `llm-creds-maas` secret. This secret was populated at provisioning time.

NOTE: While connecting OpenShift Lightspeed to MaaS works, it is not an officially supported configuration, as it adds an additional layer between OpenShift Lightspeed and the provider. OpenShift Lightspeed supports direct connectivity with the chosen model provider.

==== *Agent*

Navigate back to *Home* -> *Search*. In the *Resources* box, type `Agent` and select it from the drop-down. Open the `default` Agent and switch to the *YAML* tab:

----
apiVersion: agentic.openshift.io/v1alpha1
kind: Agent
metadata:
  name: default
spec:
  llmProvider:
    name: maas
  model: claude-sonnet-4-6
  timeouts:
    analysisSeconds: 500
    executionSeconds: 500
    verificationSeconds: 500
----

Notice the _model_ field (claude-sonnet-4-6) and the per-step _timeouts_. These can be tuned per agent. For example, you could define a _fast_ agent pointing to a smaller model for quick analysis and a _smart_ agent pointing to a more capable LLM for complex remediation, and reference them independently within the same run.

==== *ApprovalPolicy*

Lastly, go back to *Home* -> *Search*, and search for `ApprovalPolicy`. Open the `cluster` resource that appears. In the *YAML* tab you can see that all phases run automatically except for Analysis and Execution, which require manual approval:

----
apiVersion: agentic.openshift.io/v1alpha1
kind: ApprovalPolicy
metadata:
  name: cluster
spec:
  maxConcurrentRuns: 5
  stages:
    - approval: Manual
      name: Analysis
    - approval: Manual
      name: Execution
    - approval: Automatic
      name: Verification
    - approval: Automatic
      name: Escalation
----

So here's the full picture: the `LLMProvider` supplies the model provider type and credentials (pointing to the API Key secret), the `Agent` defines the model to use and timeouts for each phase, and the `ApprovalPolicy` ensures that Analysis and Execution require your sign-off while Verification and Escalation run automatically. Let's put it to work.

NOTE: Analysis never writes to the cluster, so it could safely run automatically. It is set to _Manual_ here so you can trigger and observe each phase deliberately as you learn the workflow.

[#first-agentic-run]
== Your first AgenticRun

In the previous module, you used the intelligent assistant to diagnose a broken virtual machine by attaching its YAML and asking follow-up questions. Now let's see the agent tackle a different kind of task: provisioning a workload. Instead of issuing commands step by step or composing YAML by hand, just describe what you want in plain language and submit it as an `AgenticRun`.

There are three ways to start an `AgenticRun`:

* Describe what you want in plain language and submit it directly as a manifest. The agent handles the rest: analysis, execution, and verification. This is useful for on-demand tasks like deploying a workload, checking a namespace, or scaling a resource.
* Let the Alerts Adapter do it for you. The adapter polls Alertmanager and automatically creates runs whenever firing alerts match a configured severity.
* Let the Cluster Version Operator create them when an upgrade path is available in the cluster, powering the AI-assisted analysis of update readiness.

You will start with the first one. From the *Bastion* tab, submit the following run:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: agentic.openshift.io/v1alpha1
kind: AgenticRun
metadata:
  name: deploy-test-workload
  namespace: openshift-lightspeed
spec:
  request: |
    Analyze the lightspeed-demo namespace and deploy a test workload.

    1. Analysis: List current workloads and confirm there is no Deployment
       named "hello-test" already running.
    2. Execution: Create a Deployment named "hello-test" running nginx:latest
       with 1 replica, and a ClusterIP Service named "hello-test" on port 80.
       Verify the pod reaches Running state.
  analysis:
    agent: default
  execution:
    agent: default
EOF
----

In the OpenShift web console, go to *Agentic Runs* -> *Agentic Runs* in the left navigation menu. You should see your run listed, along with the runs created automatically by the Cluster Version Operator, all in a *Pending* state, because Analysis is set to _Manual_ in the ApprovalPolicy.

Before driving it, review the approval configuration by clicking the *engine icon* in the upper-right corner. The page shows the actual approval policy and allows you to change it:

image::ols-approval-settings.png[Agentic Runs approval settings, align="center", link=self, window=blank]

As mentioned before, _Analysis_ and _Execution_ are set to _Manual_, meaning you need to trigger the analysis yourself and review the execution plan before accepting it. Do not change this configuration. Navigate back to *Agentic Runs* -> *Agentic Runs* and click on the `deploy-test-workload` run to open its detail view.

image::agentic-run.png[Agentic run view, align="center", link=self, window=blank]

Click *Approve Analysis* twice. A sandbox pod starts, queries the cluster for context, calls the LLM, and writes its findings. You can track the progress by clicking *View Analysis logs*.

Once it finishes, the agent shows different plans and is waiting for your decision before touching anything. *Select plan 1* and click the *View plan details* section to see the analysis results: confirmation that no conflicting _hello-test_ workload exists, and the plan of what will be created.

image::agentic-execute-plan.png[Select the Agentic Run proposal, align="center", link=self, window=blank]

This is the Human-in-the-Loop gate. Review the deployment plan the agent proposed. Once you agree with it, click the *Execute remediation* button twice to approve and unlock the next phase.

A new sandbox pod is deployed, the agent runs the required commands against the cluster, and reports the result. You can follow the process by clicking *View Execution logs*.

Once execution completes, *Verification* starts automatically. No further approval needed, because the verification phase was set to _Automatic_ in the ApprovalPolicy. Once the verification sandbox confirms the workload is running, the status moves to *Completed*.

NOTE: If verification determines the workload did not reach the expected state, the run transitions to *Escalation*. An escalation record is created with details for human review.

To confirm the workload was deployed, navigate to *Workloads* -> *Deployments* in the `lightspeed-demo` namespace. You should see the `hello-test` Deployment with its pod in *Running* state.

[#enabling-alerts-adapter]
== Resolving a critical alert

So far you triggered remediation manually by describing the problem and submitting the AgenticRun. The Alerts Adapter closes the remaining gap: it polls Alertmanager on a 30-second cadence and automatically creates `AgenticRun` CRs whenever firing alerts match a configured severity, so an alert can go from firing to investigated to remediated without any manual trigger.

If you recall from the Troubleshooting module, there is a `PodDisruptionBudgetLimit` critical alert firing in the cluster. Let's let the autonomous agents resolve it automatically.

The Alerts Adapter is already deployed, but its severity filter is disabled. Enable it by patching the `alerts-adapter-config` ConfigMap from the *Bastion* tab:

[source,bash,role="execute"]
----
oc patch configmap alerts-adapter-config -n openshift-lightspeed \
  --type merge -p '{"data":{"config.yaml":"pollInterval: 30s\npostRunDelay: 1h\nfiltering:\n  allowedReceivers:\n    - critical\ndeduplication:\n  ignoredLabels:\n    - pod\n    - instance\n    - endpoint\n    - uid\ntools:\n  skills:\n    - image: quay.io/openshiftanalytics/agentic-skills:latest\n      paths:\n        - /skills/cluster-troubleshoot/investigate-alert\n"}}'
----

Back in the OpenShift web console, under *Agentic Runs* -> *Agentic Runs*, you should see a new run created automatically by the adapter, called `poddisruptionbudgetlimit-critical`, in a *Pending* state. Click on it to open its detail view:

image::ols-agentic-run.png[PodDisruptionBudgetLimit AgenticRun details, align="center", link=self, window=blank]

Work through each phase of the run:

. Click *Approve Analysis* twice. A sandbox pod queries Alertmanager, inspects the affected resources, calls the LLM, and writes its findings. Track progress in *View Analysis logs*.
. Once analysis completes, review the proposed fix under the _Remediation plans_ section. If multiple execution plans appear, select the plan titled *Remove the init container*.
+
image::ols-execute-remediation.png[Remediation plans proposed by the autonomous agents, align="center", link=self, window=blank]
. Review the remediation plan in *View plan details*. Each plan provides a root cause analysis, the proposed commands, and the required permissions.
. Click *Execute remediation* twice. A sandbox pod applies the fix to the cluster. Click *View Execution logs* to follow along.
+
image::ols-execution-logs.png[Execution logs of an AgenticRun, align="center", link=self, window=blank]
. Once execution completes, *Verification* starts automatically. A new sandbox pod confirms the alert condition is resolved and the run reaches *Completed*.

To confirm the alert has been resolved, navigate to *Observe* -> *Alerting* and switch to *All projects*. The critical alert that triggered this run should no longer appear in the firing alerts list.
