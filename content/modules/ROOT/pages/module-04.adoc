= Cluster Interaction

The Cluster Interaction feature allows OpenShift Lightspeed to read and interact with your OpenShift cluster. This enables the LLM to generate highly customized responses for your environment and, when permitted, to take actions on your behalf.

image::arch-module04.svg[Architecture with the built-in MCP server highlighted]

In this module you work with the highlighted pieces: the core OpenShift Lightspeed components plus the built-in MCP server that reads and writes your cluster.

NOTE: This is currently a Technology Preview feature of OpenShift Lightspeed.

[#check-the-cluster-interaction-configuration]
== Check the Cluster Interaction Configuration

Starting with OpenShift Lightspeed 1.1, the cluster interaction feature is enabled by default on new installations, and that is how this lab environment is running. Optionally, you can check how it is enabled in the _OLSConfig_ resource.

Again, navigate to *Ecosystem* -> *Installed Operators* -> *OpenShift Lightspeed Operator* -> *OLSConfig* -> `cluster` -> *YAML*. Once in the YAML editor, scroll down until you spot the _introspectionEnabled_ flag. It should be set to _true_:

[source,yaml,role="execute",subs=attributes+]
----
...
spec:
...
  ols:
...
    introspectionEnabled: true
----

When this flag is enabled, OpenShift Lightspeed deploys `openshift-mcp-server` as a dedicated standalone pod. This server loads different toolsets — covering both read and write operations.

When a user asks a question, the model may call one or more of those tools to retrieve or modify cluster state. All tool usage is performed using the logged-in user's own credentials and access rights, preventing any privilege escalation.

NOTE: The built-in MCP server has security guardrails baked in: it is explicitly blocked from reading Secrets and RBAC resources, so sensitive data such as credentials can never reach the LLM through it — regardless of how a question is phrased or how many permissions the logged-in user has.

Important! By default, read-only tools execute automatically while write tools require explicit human approval before running — the chat interface will display the proposed tool call and ask you to confirm or reject it before anything is applied to the cluster. 

NOTE: You can change this behaviour via _approvalType_ in the OLSConfig: set it to _always_ to require approval for every tool call regardless of whether it reads or writes, or to _never_ to let all tools run without any confirmation step — though the latter is not recommended for production environments where an unreviewed write operation could have unintended consequences.

TIP: Tool calling consumes extra tokens from the model's context window. If you are tuning your own installation, _maxIterations_ limits how many tool-calling rounds the model may take per question, and the per-model _toolBudgetRatio_ setting controls how much of the context window may be spent on tool output.

[#gathering-information-from-the-cluster]
== Gathering Information from the Cluster

Now that we have seen that cluster interaction is available, you can try asking some questions about cluster resources and see how OpenShift Lightspeed responds. Open the chat interface, click the *Clear chat* (trash can) button if you have an ongoing conversation, and ask:

[source,role="execute",subs=attributes+]
----
Show me the pods in the openshift-lightspeed namespace
----

The model likely chose to use the _pods_list_in_namespace_ tool to retrieve pod information from the _openshift-lightspeed_ namespace. You can view the tool's output by clicking the `pods_list_in_namespace` button displayed after the response. This information was used by the model to generate the final answer containing the list of all pods in that namespace.

Let's take cluster interaction one step further by combining it with follow-up questions. OpenShift Lightspeed can not only gather information from your cluster but also analyze it when you ask follow-up questions within the same chat session.

For example, let's ask OpenShift Lightspeed to retrieve and analyze the logs from the last pod listed. In the same chat session, ask:

[source,role="execute",subs=attributes+]
----
Can you get and analyze the logs of the last pod?
----

OpenShift Lightspeed will use the _pods_log_ tool to retrieve the recent logs from the last pod mentioned in the previous response and then provide you with an analysis of what's happening in those logs. This demonstrates the power of combining cluster interaction with the conversational context maintained from your previous questions to navigate across different components and resources within the cluster.

Cluster interaction is not limited to Kubernetes resources. The built-in MCP server is also connected to the OpenShift monitoring stack (Prometheus and Alertmanager), which means OpenShift Lightspeed can reason about the live health of your cluster. Click the *Clear chat* (trash can) button and ask:

[source,role="execute",subs=attributes+]
----
Are there any alerts firing in the cluster right now?
----

This time the model calls the _get_alerts_ tool, retrieves the alerts currently firing from the monitoring stack, and summarizes them for you — including each alert's severity and description. As before, you can ask follow-up questions about any alert that catches your attention, and the model will combine the alert data with other cluster interaction tools to dig deeper.

[#write-tools]
== Letting Lightspeed Take Action

So far we have used cluster interaction only to read information from the cluster. But the built-in MCP server also exposes write tools — meaning OpenShift Lightspeed can make changes on your behalf, subject to your RBAC permissions.

Let's see this in action. *Clear* the chat and ask OpenShift Lightspeed to create a simple test workload in the existing _lightspeed-demo_ namespace:

[source,role="execute",subs=attributes+]
----
Create a Deployment named hello-ols in the lightspeed-demo namespace with 1 replica of registry.access.redhat.com/ubi9/ubi, command sleep and argument infinity. Do not set fsGroup in the pod security context.
----

OpenShift Lightspeed will invoke the _resources_create_or_update_ tool to apply the Deployment manifest. As it is an operation that writes to your cluster, you will be asked to approve or reject the action. Go ahead and click *Approve*.

image::approve-tool.png[Approve write execution MCP tool,600]

Once approved, you can verify it in the console under *Workloads* -> *Deployments* in the `lightspeed-demo` namespace.

Now scale it up to see another write tool in action:

[source,role="execute",subs=attributes+]
----
Scale the hello-ols Deployment to 3 replicas
----

OpenShift Lightspeed calls _resources_scale_. *Approve* the execution again. Then check the Deployments view to confirm the replica count changes to 3.

Finally, clean up the demo resource:

[source,role="execute",subs=attributes+]
----
Delete the hello-ols Deployment
----

*Approve* the _resources_delete_ tool execution. The deployment should disappear from your cluster.

== What if there's something wrong?

In the examples above, we saw that the pods were running healthy and their logs showed no issues. But what happens when you're actually facing a real problem that needs troubleshooting?

One powerful feature of OpenShift Lightspeed is the ability to attach resource information directly to your questions. By attaching YAML manifests, logs, or events from problematic resources, you provide OpenShift Lightspeed with the specific context it needs to diagnose issues effectively. Let's put this into practice in the next module by diagnosing and resolving a real issue in your cluster.
