= Bring Your Own Knowledge

include::partial$console-access.adoc[]

Most organizations that have been using OpenShift Container Platform for any length of time have developed their own policies, procedures, templates, and other organization-specific information about OpenShift.

As you learned earlier, the intelligent assistant only uses Red Hat documentation to support answers by default. So, how can you get your important internal knowledge into the system? Well, there's a feature for that called Bring Your Own Knowledge (BYOK).

image::arch-module02.svg[Architecture with the RAG databases highlighted, align="center", link=self, window=blank]

In this module you work with the highlighted pieces: the vector databases that ground the assistant's answers.

NOTE: This is currently a Technology Preview feature of OpenShift Lightspeed.

[#examine-the-bring-your-own-knowledge-configuration]
== Examine the Bring Your Own Knowledge configuration

The OpenShift Lightspeed Operator has been pre-configured in this lab environment to point to a container image with ACME Corp-specific knowledge. Let's examine this configuration to understand how BYOK works.

NOTE: In this module you consume a BYOK image that has already been built. Alternatively the official https://docs.redhat.com/en/documentation/red_hat_openshift_lightspeed/1.0/html/configure/ols-configuring-openshift-lightspeed#about-the-byo-knowledge-tool_ols-configuring-openshift-lightspeed[Bring Your Own Knowledge documentation] covers the podman-based workflow.

In the OpenShift web console, navigate to *Ecosystem* -> *Installed Operators* -> *OpenShift Lightspeed Operator* -> *OLSConfig* -> `cluster` -> *YAML*. Once in the YAML editor, scroll down until you spot the _rag_ stanza. It should look something like:

----
...
spec:
...
  ols:
...
    rag:
      - image: 'quay.io/dialvare/acme-byok:latest'
        indexID: ''
        indexPath: /rag/vector_db
----

NOTE: You can define multiple RAG databases if you want to add multiple sources. The _rag_ stanza just takes an array of image references. Images hosted in private registries are supported too, via the _imagePullSecrets_ field. If you want the assistant to answer *exclusively* from your own content, you can additionally set _byokRAGOnly: true_, which tells it to ignore the built-in RHOKP documentation entirely.

[#check-the-internal-documentation]
== Check the internal documentation

As you just saw, the assistant is configured to use a container image from Quay (`quay.io/dialvare/acme-byok:latest`) that contains ACME Corp's internal procedures and policies. But where does this content come from?

This BYOK image was built from Markdown docs. The documentation used is located in this https://github.com/dialvare/showroom-openshift-lightspeed/tree/main/byok[GitHub repository] and consists of three documents:

* The specific ACME process for horizontal pod autoscaling
* The specific ACME process for adding GPU nodes
* Vendor-supplied documentation for the Dell APEX Cloud Platform API gateway certificate

Take a look at those to get an understanding of what they are discussing. Notice that BYOK is not limited to internal policy documents: the third document is an example of vendor or partner documentation that is not part of the official OpenShift documentation set, but that your teams may rely on every day.

[#byok-enters-the-chat]
== BYOK enters the chat

Now that you know the contents of the internal ACME Corp policies and that the assistant is pointing to the additional RAG database, you should be able to get answers based on that custom knowledge and content.

If you closed the chat window, reopen it. Make sure to click the *Clear chat* button, which appears once a conversation is underway, and then ask the following question:

[source,role="copypaste"]
----
How can I use a pod autoscaler at ACME Corp?
----

You should see an answer that refers to the prohibition on autoscalers and the specific processes required to get one. At the end of the response, the chatbot also shows the most relevant custom documents provided in the BYOK image.

The assistant assigns greater weight to BYOK content, so your internal procedures take precedence over the default RHOKP documentation when generating responses.

Try asking questions about adding GPU nodes or about the APEX Cloud Platform API gateway certificate and see if you can get responses based on the embedded documentation.
